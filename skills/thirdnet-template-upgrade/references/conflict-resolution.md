# 冲突处理规范（Phase 3 决策核心）

> 本文件在 Phase 3 遇到 ⚠️ `Conflict` 文件时**必读**。冲突 = 用户改过、模板也改过，工具无法自动决定取舍，需要你逐文件决策。

对每个 ⚠️ `Conflict` 文件，按以下规则决策。

**经验总则：框架/基础设施代码以模板为准，业务代码以用户为准。** 理解这条总则的内核——模板的改动通常是 bug 修复、框架升级、结构优化，对框架文件应优先信任模板；而用户的改动承载业务逻辑，对业务文件必须优先信任用户。判断每个文件属于哪一类，是正确决策的关键。

## 决策矩阵

按文件类型匹配，给出默认决策方向：

| 文件类型 | 用户通常改什么 | 模板侧可能变更 | 决策 |
|----------|----------------|----------------|------|
| `Startup.cs` / DI 配置 | 注册业务 Service、加业务中间件、改认证 | 新增框架级 DI、调整中间件顺序 | **`[m]` 手动合并**：保留用户业务注册行，吸收模板框架注册行；两边 `AddThirdNet*` 框架调用**以模板为准** |
| `Program.cs` | 改端口、加配置源 | 启动流程微调 | **`[a]` 套用模板**为主，移植用户特有配置 |
| `appsettings.json` | 连接字符串、业务配置 | 新增框架配置节 | **`[m]` 手动合并**：保留用户值，补齐模板新增键 |
| 业务 `*DbContext.cs` / 实体 / EntityConfiguration | 加业务 `DbSet<>`、业务映射 | 几乎不变（多为 `UserOnly`，少有 Conflict） | 通常保留；若 Conflict 则 `[k]` 或逐行确认 |
| Controller 基类 / 权限 / 认证框架文件 | 少见 | 框架逻辑修复 | **`[a]` 套用模板**（框架修复通常更正确），除非用户改动有明确业务理由 |
| 纯业务 Controller / Service / DTO | 用户业务实现 | 模板一般不动（应为 `UserOnly`） | 若误报为 Conflict，`[k]` 保留 |

## 决策步骤（每个 Conflict 文件）

1. 用 `[v]` 查看完整 diff：你的版本 → 新模板，**以及上游变更（旧基线 → 新模板）**。同时看「用户改了什么」和「模板改了什么」这两条线，才能判断该保留谁。
2. 判断用户的每处改动属于：
   - **业务扩展**（新增方法 / 注册 / 路由 / 配置值）→ 必须保留。
   - **对框架代码的早期微调**（通常踩坑临时改的）→ 倾向采用模板新版。
3. 选择：
   - 改动简单、可清晰叠加 → `[a]` 套用模板后**立即把用户业务改动重新加回**（在本次升级内完成，不要留到以后）。
   - 改动复杂、需逐行取舍 → `[m]` 生成冲突标记文件，按下方规范合并。
   - 拿不准 → `[e]` 稍后决定，**单独评估后再处理**，绝不盲目 `[a]`。
4. **禁止用 `--force`** 处理业务相关 Conflict。

## 冲突标记文件（`.thirdnet.merge`）合并规范

选 `[m]` 后生成 `<原文件>.thirdnet.merge`，格式：
```
<<<<<<< MINE (<相对路径> 用户当前版本)
<用户内容>
=======
<新模板内容>
>>>>>>> TEMPLATE (v<目标版本>)
```

合并步骤：
1. 读取该文件，按「决策矩阵」+「决策步骤」规则决定每段取舍，合成最终内容。原则不变：业务扩展保留 + 框架更新吸收。
2. 用合成内容**覆盖原文件**。
3. 删除 `.thirdnet.merge` 文件。
4. 该文件因已人为改过，下次 diff 会识别为 `UserOnly`（保留），不会再冲突——这是**预期的**，不要误以为是问题。
5. 重新 `dotnet build` 验证。

> 合并后务必回到 Phase 4 编译验证。`Startup.cs` 这类文件最易因漏注册某个框架服务而编译失败，看到编译错误优先回查合并文件。

## 前端冲突处理（前端轨道）

> 前端的"冲突"对应 diff 输出里的两类，都没有 `[m]`、没有 `.thirdnet.merge` 文件——这是前端相对后端的简化，也是能力差距。
>
> - **⚠️ 已修改（需确认）** = `Modified` 且 `userModified` 且非 override：用户改过、模板也改了，需逐文件决策。
> - **🔒 品牌文件（自动跳过，需手动集成）** = `Modified` 且 `isOverride`：apply 不会动，必须在工具外手动合并。

### 决策选项（前端只有三个）

apply 对每个 ⚠️ 文件提示 `[a]应用 [s]跳过 [v]查看完整diff`（默认 `s`）：

- `[a]` 应用模板版 —— 确认这是框架文件、用户改动可弃时选。
- `[s]` 跳过、保留我的版本 —— **业务文件默认选这个**。
- `[v]` 查看完整 diff —— 信息不足时先看，随后再 `[a]`/`[s]`。

> 复杂冲突（需同时保留用户的业务改动和模板的框架改动）只能 `[s]` 跳过，**apply 完成后在编辑器里手动合并**——参考 Phase 2 diff 的上游预览，把模板改动叠加进你的文件。前端没有后端那种"写冲突标记文件、稍后合并"的机制。

### 前端文件类型决策方向

总则不变：**框架/基础设施代码以模板为准，业务代码以用户为准。**

| 文件 | 属于 | 决策方向 |
|------|------|----------|
| `src/api/`、`src/stores/`、`src/composables/`、`src/layouts/`、`src/router/`、`src/utils/`、`src/directives/`、`src/mock/`、`src/styles/`、`src/components/` | 框架资产 | 倾向 `[a]`（模板的 bug 修复/重构通常更对），除非你有明确的业务理由 |
| `src/views/` 下你的业务页面、用户自定义文件 | 业务代码 | 倾向 `[s]`；要吸收模板改动就手动合并 |
| 受保护目录 `src/views/system`、`src/views/api`、`src/api/modules/manager` 的业务逻辑 | 模板资产（按 frontend-workflow 规则本就不该改） | 正常应是 ✅ 安全自动；若出现在 ⚠️，说明曾被违反——按业务优先逐行取舍 |

### 🔒 品牌文件（override）的手动合并

这 4 个文件 apply 自动跳过，**必须手动合并**（详见 [frontend-flow](frontend-flow.md) 的 Phase 3.5）：

- `package.json` —— **依赖版本升级**是前端最常见的合并点：把模板新增/升级的依赖（Element Plus / Vite / Vue / Pinia 等）同步进你的 `dependencies/devDependencies`，保留你的项目名与业务依赖。合并后必须 `npm install`。
- `vite.config.ts`、`index.html`、`src/config/brand.ts` —— 对照 diff 的上游预览，吸收模板的结构/配置调整，保留你的品牌值。

合并完务必回到 Phase 4 跑 `npm run build` 验证。
