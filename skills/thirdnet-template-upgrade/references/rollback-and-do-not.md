# 回滚预案与禁止事项（第 8–9 章）

> 本文件收录两件事：升级出问题时的**回滚**方法，以及**绝对不能做**的事项清单。执行升级前复核红线，出问题时按回滚优先级恢复。

## 第 8 章 回滚预案

升级出问题时的回滚优先级（从最可靠到兜底）：

1. **首选（最干净）：`git reset --hard <升级前 commit>`** —— 因 Phase 0 已保证工作区干净，这是最可靠的一键回滚。前提是升级前那次 commit 的哈希已记录。
2. **工具自动备份**：`.thirdnet-backup/<时间戳>/` 下有被覆盖文件的原始副本（文件名是原路径的扁平化）。逐个还原即可，但不如 git 干净。
3. **回滚文件时务必一并还原 `.template-version.json` 与 `.template-manifest.json`**，否则下次 diff 的基准会错乱——这两个文件定义了「当前是什么版本」，错乱会让后续升级全乱。

## 第 9 章 禁止事项清单（DO NOT）

这些事项每一条都对应一次真实事故或一类高风险。理解为什么禁止，比死记更有效：

- ❌ **用 `--force` 批量覆盖含业务逻辑的 Conflict 文件。** `--force` 绕过逐个确认 = 盲覆盖，业务代码一旦被覆盖、git 又没及时回滚就丢失。
- ❌ **手动删除任何用户文件（即便模板删了它）。** 模板删文件可能只是重构，用户项目里那文件可能仍承载业务。apply 的「仅提示永不删」是有意为之。
- ❌ **手动改 `ThirdNetVibe` 命名空间引用或 `VIBE_*` 占位符。** 工具在比对前会自动替换，手动改会让干净的 UpstreamOnly 变成假 Conflict，制造混乱。
- ❌ **在 git 工作区不干净时升级。** 干净工作区是第一道回滚保险，脏工作区会让 `git reset --hard` 连未提交的工作一起冲掉。
- ❌ **手动编辑 `.template-manifest.json`**（除非明确按 7.1/7.3 的流程由工具重建）。清单是工具维护的哈希基准，手改会让后续 diff 全错。
- ❌ **跳过 `diff` 直接 `apply`。** diff 是唯一让你看清「将要发生什么」的只读预览，跳过等于盲操作。
- ❌ **升级到尚未发布到服务器的模板版本**（除非用 `--nupkg` 提供本地包）。未发布的改动拿不到，强行升级只会得到旧模板。
- ❌ **升级后不跑 `dotnet build` 验证就提交。** 合并 Conflict 文件最易引入编译错误，提交前必须编译通过。
