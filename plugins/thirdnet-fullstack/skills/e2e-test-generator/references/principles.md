# 5 条原则（深入讲解）

这些是每条生成的测试都遵守的不变量。理解*为什么*比死记字面更重要——把道理内化后，再按每个项目的实际情况做判断。

## 1. 纯 UI 驱动——定义性铁律

**做：** 打开真实弹窗，按 label/placeholder 填表，点提交，从表格/列表 DOM 读回结果。

**不做：** 从测试工具里调后端（`requests`、`urllib`、`fetch`、某个 `ApiClient`）。

**为什么：** 目标是抓 *UI 层* bug——弹窗没接上、字段绑到了错误的 model、前端校验缺失/错误、权限指令隐藏错了按钮、状态字段渲染成了错误的控件。API 驱动的测试把这一切都绕过了：它们证明后端能用，却从不碰用户真正会去摸的那层 UI。纯 UI 测试在 UI 错的时候失败——这正是重点。

唯一发生的 HTTP 是**被测前端自己**发出的（它自己的 axios/uni.request 调用）。测试工具驱动 DOM；前端做其余的事。只断言 DOM 文本。

**你正在违规的信号：** 你正要在某个 test 或 lib 文件里写 `api.get(...)` / `ApiClient(...)` / `urllib.request`。停下来，换成一次 UI 操作（开弹窗、填表、提交、`read_cell`）。

## 2. 写入即回验

**每一次** create / update / delete 之后，在往下走之前，立即在同一端的 DOM 里确认效果：
- create → 行/卡片出现（按 name/title 匹配），
- update → 字段变了，
- delete → 行没了，
- 状态流转 → 状态列/单元格文本变了。

**为什么：**「提交返回成功」≠「它真的落库并渲染了」。回验能抓到静默保存失败、列表没刷新、写错字段。这是整套件里最便宜、价值最高的断言。

用这样的辅助函数实现：`assert_row_exists(keyword)`、`assert_row_gone(keyword)`、`read_cell(keyword, column_label)`。

## 3. 跨端一致性

当在一端产生的数据应当能在另一端可见/正确时，也在那端断言：
- B 端发布公告 → 范围内的 C 端用户能看到，范围外的看不到。
- C 端提交一条工单/订单 → B 端列表显示它（状态待处理）→ 驾驶舱把它计入。
- B 端创建一个资源 → 驾驶舱该资源总数反映出来。

**为什么：** 集成 bug 就藏在这儿——一条记录在一端存了却在另一端看不见，通常意味着范围/过滤/缓存的 bug。跨端断言正是这类问题的回归网。

每条跨端测试都用对的账号登录两端、在每端断言 DOM。

## 4. 多角色 + 数据范围 + 负向（「按钮不存在」模式）

在**多个权限有别的账号**下测试。对每个范围受限的角色：
- 断言它只看到自己的数据范围（只自己的组织/租户/部门；不是兄弟部门的），
- 对它**无**权限的动作，断言按钮或菜单**在 DOM 中不存在**（count 为 0），而不是断言会触发 403。

**为什么权限指令（如 `v-permission`）是在客户端隐藏无权限控件的。** 真实用户体验是「按钮压根不在那儿」——所以正确、稳健的断言是 `expect(button).to_have_count(0)`。断言 403 要求按钮存在并能点，这 (a) 不够忠实，(b) 会发一个真实请求污染被动监听器，(c) 一旦指令改成「渲染再禁用」而非「隐藏」就崩。DOM 不存在严格更优。

数据范围正向：角色 A 看到实体 A，看不到实体 B。负向：角色 A 在该实体页没有「新增」按钮。

## 5. 被动监听（只观察，不连接）

给**每个** page 挂监听器：`console`（error/warning）、`pageerror`（未捕获异常）、`response`（4xx/5xx）。这些*观察的是前端自身的行为*——**不是**测试工具在连后端。它们是整套件的首要抓 bug 网：一条通过的流程里出现 console 报错或意外的 5xx，就是一个真实发现。

**预期内的失败：** 有些 4xx 是预期的（例如前端预检放过了重复/重叠，后端返回冲突 409）。通过一个 `expect_response(url_substring, status)` 机制把它们登记起来，这样监听器就不会把它们标成 bug。原则是：*把预期内的失败显式标记；其余的全部上报。*

这些发现汇总进测试报告 + `findings.json`，与 pass/fail 分开。

## 各原则如何在单条测试里组合

一条跨端工单/订单流程（C 提交 → B 处理 → 驾驶舱）：
- **P1** C 填真实表单（chip + 字段）→ 提交 → 读 toast。
- **P2** C 的列表显示该记录，状态「待处理」；B 的列表也显示它，状态「待处理」。
- **P3** B 受理/处理 → 状态「处理中」；该流程的驾驶舱面板渲染出来。
- **P4** 用一个范围受限的角色跑一遍——只看到自己的记录；无权限的角色根本没那条流程的菜单项。
- **P5** 全程捕获 console/pageerror/5xx；预期的 409（如有冲突子分支）预先登记好。

套件里的每条测试都该长这样——每条原则都体现为具体的断言。
