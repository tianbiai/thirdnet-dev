# 探索——阶段 1 的 Explore 操作手册

这是让套件*贴合具体项目*的引擎。你从真实代码里提取**真实的** selector/label/流程/权限——**只读代码，不连接、不启动、不探活待测系统**——绝不猜，绝不假设某个框架的默认值。派发并行 Explore 子代理（下面每个关注点一个），然后汇总。

> Explore 子代理返回的是结论/摘录，不是文件堆。给每个子代理一个明确的关注点，并要求它给出你会直接写进 `selectors.py` 的*确切字符串*。

## 按关注点探索什么

### A. Web 组件库 + 表单/表格原子
**目标：** 搞清楚一个表单项、一张表格、一个弹窗、一个 select、一个 radio、一个 tree-select 各是怎么渲染的，这样你的 `fill_*`/`read_cell` 辅助函数才能命中对的 DOM。
**读：** UI 框架的组件文件 + 2–3 个有代表性的 CRUD 页（`views/<entity>/index.vue`）。
**提取并记录：**
- 表单项容器 + label 选择器（如 Element Plus：`.el-form-item` + `.el-form-item__label`）。
- input/textarea/select/radio/switch/tree-select/time-select 的 class。
- 表格行 + 表头单元格的 class（用于按列头 `read_cell`）。
- 弹窗外壳 + 提交按钮文案（常见是「确定」/「提交」；有些弹窗用别的动词，如「发送」）。
- **易踩的坑：** `status` 是 radio 还是 select？某个 `<select>` 要用 `fill_select` 还是自定义 picker？有没有动态 tab 锁定（如分类 tab 控制哪些字段显示）？

### B. 确切的字段 label、placeholder、按钮文案、表头
**目标：** 测试要命中的字面字符串。
**读：** 每个业务模块的创建/编辑弹窗模板 + 列表页。
**提取并记录**（每个实体）：每个表单 `label`、每个 `placeholder`、每个动作按钮文案（新增/编辑/删除/发布/下架/通过/受理/完成/回复/...）、每个表格列头（注意异常：有的首列是「ID」，有的是业务编码如「工单号」/「编号」；有的状态列是只读的）。
→ 这些直接进 `selectors.py` 和实体构造器。

### C. 业务流 + 状态机
**目标：** 每条流程是什么、状态怎么流转。
**读：** 后端 controller（路由特性——.NET `[Route]`、Spring `@RequestMapping`、Express 装饰器等——给出路由前缀，别猜）+ service 层 + 项目的 `spec.md`/`specs/*.md`。
**提取并记录：**
- 每个实体及其 CRUD 端点（用于理解，**不是**为了去调）。
- 每条多步流程及其状态机（如工单流：待受理→处理中→已完成；审批流：待审批→已通过/已拒绝；访客流：待确认→已通过/已取消）。
- 哪些流程跨端（C 创建 → B 处理 → 驾驶舱显示）。
- 前端执行的校验/冲突规则（如时间重叠或重复 → toast + 不跳转；后端 409 兜底）。

### D. 认证、权限、数据范围
**目标：** 怎么以每个角色登录、每个角色能看到什么、无权限控件怎么被隐藏。
**读：** 登录页 + auth store + 权限指令（如 `v-permission`）+ 数据范围辅助类（如某个 operator-context / scope-helper 类，带一个「是否含下级部门」标志——确切名字按后端各异）+ 角色/用户管理弹窗。
**提取并记录：**
- 登录流程（web：用户名/密码/验证码按钮文案；移动端：微信一键 / 账号 / 绑定流程）。
- 权限指令名 + 它如何隐藏控件（从 DOM 移除 vs 禁用）→ 确认「按钮不存在」负向模式成立。
- 数据范围机制（用户级部门 + include_sub_depts？超管通配？）→ 告诉你怎么断言范围。
- 角色准备 UI：菜单怎么分配（如一棵 `el-tree` 按**可见菜单名**勾选，而非权限串）、用户怎么分配角色/部门。
- 种子超管凭据（用于脚手架/角色准备阶段）。

### E. 移动端（如有）
**目标：** 移动端组件原子（通常是自研库，**不是** Vant/Element）。
**读：** 移动端组件目录（`components/*.vue`——项目自研的移动端库）+ 2–3 个页面。
**提取并记录：**
- 字段组件 DOM（容器/label/input/textarea/error 的 class）。
- Toast + 弹窗 class 以及确认/取消按钮选择器 + toast 停留多久（影响等待时机）。
- Chip/tab/submit 选择器。
- **原生 `<picker>`**（日期/时间/范围）：它在 H5 里怎么渲染（如 `<uni-picker>` → `.uni-picker` 滚轮列 + 确认按钮）。它**不是**原生 `<select>`，也**不是**日历弹层。从真实 DOM 建辅助函数是必须的；把它作为**校准点**标在 README 里。
- 列表卡片 class 用于回验（卡片标题 + 状态徽章 + 标签 class）。

## 产出物

1. **探索笔记**（留在你的工作上下文 / 草稿文档里）：每条流程的小结 + 状态机 + 每个实体的字段清单 + 认证/范围发现 + 易踩的坑。这喂给 `TEST_PLAN.md`（阶段 2）。
2. **`selectors.py` 草稿**：每个 label/placeholder/按钮文案/路由/class，分组（登录、web 菜单、web 原子、移动端原子、路由）。这喂给阶段 3。

## 要避免的反模式

- **照框架文档猜 selector。** 项目可能包裹/覆写了组件。一律对着真实模板源确认。
- **写死路由前缀。** 读 controller 的路由特性；有的模块会出乎意料（例如某个 controller 路由是 `/api/<module-a>/...` 却放在 `<module-b>` 命名空间下）。菜单可靠时优先走侧边栏菜单导航，而非写死路径。
- **跳过权限指令。** 如果你不确认无权限按钮*怎么*被隐藏，你的负向用例就是错的。
- **以为原生 picker 已搞定。** 并没有——它是一个要记录的校准点。从真实 DOM 建辅助函数，并告诉用户首次运行时要微调。
