# 需求收集（Intake）—— 把用户输入转成 Park Spec

每一次任务都从对输入分类、把它转换成一份 **Park Spec 草稿**（`references/park-spec.md`）开始，然后与用户确认。四种输入模式需要不同的工具。在下文挑选匹配的章节。

无论哪种模式，需求收集的目标都一样：结束时拿到一份完整且通过校验的 spec（`python scripts/validate_spec.py <spec.json>` 返回 `OK`）。用 `AskUserQuestion` 来填补缺口而不是瞎猜——尤其位置和尺寸应由用户决定。

## 通用访谈问题（每种模式都要问）

这些字段无法从任何输入中推断，必须确认：
- **标题** —— “{园区名}”（页面/文档标题）。
- **视觉风格** —— 赛博（默认）/ 真实物体 / 夜间写实 / 蓝图 / 全息 / 白模 / 等距插画，7 选 1（写入 `spec.style`；细则见 `references/styles.md`）。
- **位置/尺寸** —— 每栋楼的占地与坐标应由用户决定（你只能给默认排布）。地下车库只需确认入口位置与朝向（`facing`，默认朝南），**不再问车位数**（v1.3 起车库不显示占用）。

## 环境与氛围（智能默认 + 询问）

v1.2 起场景不再只是「楼栋 + 地面」——会生成园区内部道路、地面车位、绿化、周边市政道路、围墙、路灯等环境元素（见 `references/scene-recipe.md §10`、schema 见 `references/park-spec.md` 的 `ParkEnvironment`）。**这一组问题不是必答**：用户不答就用智能默认产出一张完整全景；但主动询问能更贴近真实园区，显著提升数字孪生的真实感。用 `AskUserQuestion` 分批问（每次 ≤4 个）：

- **地面车位** —— 园区有没有地面车位？大概多少个？（默认：按楼栋规模推算，如每栋 ~6 个 × 楼层数合计）。写入 `spec.environment.surfaceParking = { stalls }`；无则 `null`。**v1.4 起**地面车位为长方形车位 + 每位印 P + 默认约 30% 车位放汽车示意停放——可选问「大概停了几成车？」写入 `occupied`（不问则默认 ~30%）。
- **绿化密度** —— 稀疏 / 普通 / 茂密？要中央广场吗？有水景/水池吗？（默认：普通 + 中央广场、无水景）。写入 `spec.environment.greenery`。
- **周边道路** —— 园区四面是否临市政道路？有围墙/护栏吗？有主出入口闸机吗？（默认：四面临路 + 围墙 + 主闸机）。写入 `spec.environment.surrounding`。
- **氛围细节** —— 要路灯吗（夜间写实风格下会发光）？地面发光标线开吗（仅赛博）？周边要放少量车辆/行人代理体吗？（默认：开路灯；发光标线仅赛博开；放车辆）。写入 `spec.environment.ambiance`。

只要用户答了任一项，就把整组写进 `spec.environment`；用户完全没提环境时，**省略 `environment` 字段**（生成器走智能默认），不要塞一个空对象。

## 兴趣点 POI（智能默认 + 询问；v1.3 新增）

数字孪生驾驶舱通常要在地图上打点标注关键设施：出入口、监控摄像头、闸机/道闸、服务点、地标等。每个 POI 由**类型（驱动图标+颜色）+ 坐标 + 可选提示数据**描述，全部写入 `spec.pois`（schema 见 `references/park-spec.md`，生成细则见 `references/scene-recipe.md §11`）。**这一组不是必答**：用户不答就 `pois: []`（不生成 POI）；但主动询问能显著提升驾驶舱的运营价值。

用 `AskUserQuestion` 分批问（每次 ≤4 个）：
- **要打哪些点？** —— 列出类型（出入口 entrance/出口 exit/监控 camera/闸机 gate/服务点 service/地标 landmark/停车场 parking/其它 custom），让用户勾选要哪些。
- **每个点的位置与名称** —— 名称（`label`）；位置可由用户在草图上指认，或直接给世界坐标 `{x, z}`（在 `boundary` 内）。室内点位还可绑 `buildingId` + `floorIndex`。
- **提示卡内容（可选）** —— 要不要悬停/点击弹出提示？若要，问 `tooltip.description`（简述）和 `tooltip.meta`（键值对，如 负责人/电话/状态/容量）。

只要用户给了任何一个 POI，就写进 `spec.pois` 数组；完全没提则省略 `pois` 字段。

## 楼层单位（后台可配置）

楼层 → 单位映射（`floors_detail`，每层一个或多个单位）本来就是 spec 驱动、后台可配置的——v1.3 起明确：每层 `units` 数组承载一个或多个单位（详见 `references/park-spec.md` 的 `FloorSpec` / `UnitDetail`）。如果用户给了「某层有哪些单位」的清单，务必写进 `floors_detail`，而不要只在 `header` 里写「N单位」。

## 模式 A —— 文字需求 + 访谈

用户用散文或清单描述园区（“3 栋楼：研发楼 12 层、办公楼 6 层、会展中心 3 层，地下车库在南侧”）。

1. 把显式事实解析进 spec 草稿：楼栋（名称、楼层）、关键单位、车库入口位置/朝向。
2. 给 `w`/`d`/`x`/`z` 填一个合理的默认排布（在 `boundary` 内沿 左上→右下 对角线展开），然后与用户**确认布局**——他们可能有真实的地块规划。
3. 用 `AskUserQuestion`（每次调用最多 4 个问题）问上面的通用问题，以及任何缺失项（例如他们想要详情视图里每层的租户名）。
4. 写出 spec JSON，运行 `validate_spec.py`，给用户展示一份精简摘要，确认后继续。

楼层+单位推导出的默认头标文字：`"{floors}F · {units}单位"`（单位可选）。

## 模式 B —— 手绘草图

用户上传一张手绘布局的照片/扫描件。

1. **用 `Read` 工具读取图像**（它会渲染图像），或用 `zai` 图像分析 MCP（`analyze_image`）做一遍结构化提取。抽取：
   - **楼栋数量**和它们的**相对位置**（在哪个角 / 中央 / 如何分布）。
   - **相对高度**（哪栋塔楼最高）→ 排序，然后通过提问分配 `floors`。
   - **任何手写文字**（楼名、入口箭头、“P”/车库）。
   - 道路、绿化、入口（这些会变成可选的装饰）。
2. 如果草图上标了车库区域或「P」标记，标记出来（v1.3 起车库只画入口，不需要车位数）。
3. 草图给你的是**拓扑**，不是数字——所以要问：每栋楼的层数、标题、主题。用通用问题。
4. 把草图位置映射到世界坐标：按比例在 `boundary` 内放置楼栋；最高那栋大致居中，其余散开。生成后用截图确认。
5. 写出 + 校验 spec。

## 模式 C —— 效果图 / rendering

用户上传一张目标效果图或驾驶舱截图。

1. **读取图像**（或 `zai analyze_image`）并抽取：
   - **配色/风格** —— 主导背景色 + 强调色。先判断最接近 7 种风格里的哪一种（赛博=霓虹深底/发光网格，真实物体=日间 PBR，夜间写实=夜空+灯光，蓝图=深蓝图底+白线框坐标网格，全息=暗底+半透青玻璃+边缘辉光，白模=全白磨砂+软阴影，等距插画=flatShading 鲜活彩色），定下 `spec.style`；再用 `spec.tokens` 做细微覆盖匹配效果图配色。
   - **相机角度** —— 等轴/透视/俯视。默认是正交等轴；如果效果图要透视，记下来。
   - **楼栋风格** —— 玻璃幕墙、边缘发光、天线、屋顶类型。记下所选风格配方没覆盖的任何东西（比如一个地标造型），单独处理。
   - **屏幕上的界面元素** —— 是否有图例、POI 标记/提示卡？这些都属于数字孪生模块本身（见 `references/scene-recipe.md`、`shell.md`）。效果图里的外围侧栏/面板**不再由本技能生成**——留空。
   - **任何可读文字**（楼名、楼层标签、POI 标签）。
2. 决策：忠实换肤（选定 `spec.style` + 编辑 `tokens` 去匹配效果图的配色）vs 保持风格默认但采用效果图的布局。与用户确认——这是本模式的主分叉。
3. 像模式 B 一样提取拓扑（位置/高度），然后问数字。
4. 写出 + 校验 spec。

## 模式 D —— Pencil `.pen` 设计源

最精确的模式。`.pen` 是事实来源。

1. **运行抽取器**（黑盒）：`python scripts/extract_pen.py <file.pen> --out spec.json`。它把 token、grid uniform、楼栋头信息（名称/楼层/单位）、图例和标题拉进一份草稿（v1.3 起不再抽车库占用数字），把 `id`/`w`/`d`/`x`/`z` 留为 null。参见 `evals/files/sample-pen-extract.json` 了解产出长什么样。
   - 如果脚本报告 `.pen` 不是 UTF-8 JSON（加密/二进制），改用 **pencil MCP**：`get_editor_state` → 对 Scene 帧 `batch_get`。参见 `references/design-source.md`。
2. **填补 null 值**，方法是读取 Scene 布局。`.pen` 的 Scene 是一幅等轴矢量插图——每栋楼是一组绝对定位的 path 部件。读取 Scene 帧的子节点（pencil `batch_get`，readDepth 4），用部件的位置/尺寸在 spec 的世界单位里估算 `w`/`d`/`x`/`z`（把等轴插图的像素空间缩放到世界 boundary）。用截图确认。
3. **分配类别**：为 地下车库 添加 `garage` 类别的楼栋并设 `facing`（朝向）；其余每栋楼都是 `building`。
4. 写出 + 校验 spec。

## 需求收集之后（所有模式）

- `python scripts/validate_spec.py <spec.json>` —— 修掉每一个 `FAIL:`。
- 给用户展示一段摘要（标题、按类别计的 N 栋楼、车库入口、主题、**环境元素清单**：内部道路/地面车位/绿化/周边道路/路灯、**POI 清单**：类型+坐标）以及切换器标签页列表。确认后进入生成；如果他们要改某项，编辑 spec（不要改生成器）。
