# 项目文档生成指南

基于代码库现有功能模块，按模板生成四类标准交付文档（亦可生成用户自定义的其它文档类型）。

## 文档写作原则（重要）

交付文档默认面向**业务人员**（兼顾评审、验收与终端用户），不是给开发者看的代码清单。本技能产出的文档必须遵循：

- **用词通俗易懂**：以日常业务语言为主；当某个技术概念无法回避时，用一句话通俗解释，不要直接抛术语。避免出现表名、接口路由、权限串、框架缩写等开发向词汇。这是默认基调——除非用户在 Step 1 明确指定其它读者，否则一律按业务人员能读懂的标准来写。
- **以功能、业务流程、设计理念为主线**：每类文档围绕"系统能做什么、业务怎么流转、为什么这样设计"展开。
- **禁止堆砌代码级细节**：不要把表名（`t_xxx`）、字段类型与可空、索引名、接口路由（`/api/...`）、DTO `Map` 后缀、权限串（`module:entity:action`）写进交付文档。这些属于 `spec.md` 等开发文档的范畴。
- **概念化表达技术内容**：
  - 数据 → 用"核心数据对象 + 对象间关系"描述，必要时附概念关系图
  - 接口 → 按功能分组说明"做什么、何时触发、输入输出概念"，而非罗列路由与类型签名
  - 权限 → 用角色与业务语言（谁能做什么），不写权限串
  - 安全/缓存/任务 → 讲策略与用途，不贴代码片段
- **读者适配**：用户手册保持终端用户语言（无技术词汇）；需求规格与系统设计停留在设计与业务层；测试用例以业务行为为粒度。
- **需求规格 vs 测试用例分工**：需求规格说明书描述"系统应提供什么能力、业务如何流转、受哪些规则约束"（功能 / 业务流程 / 业务规则 / 注意事项）；测试用例文档描述"如何验证这些能力"（操作步骤 / 输入输出 / 预期）。两者不重复——用例（前置条件、操作步骤、预期结果）只出现在测试用例文档，需求规格不写用例表。

> 扫描代码是为了**理解业务**（搞清功能、流程、模块职责），不是为了把代码搬进文档。代码层信息仅辅助归纳，必要时可在文档末尾"备注"中提示开发参考 `spec.md`。

## 文档与代码同源

"同源"指**事实一致**——文档里写的功能、字段含义、业务规则要与代码实际行为吻合，能从代码确认的事实就直接采用，不从代码可得的业务背景、优先级、验收标准才向用户追问，杜绝臆造。这与"不堆砌代码细节"不矛盾：用业务语言忠实描述代码反映的事实即可。

## 标准工作流

> **两条路径**：用户**明确点名一类**（如"生成用户手册"）→ 走单类线性 5 步（Step 2 按该类型采集、单文件填充）。用户**点名多类或泛指**（如"出用户手册和测试用例""生成项目交付文档"）→ 走批量路径：Step 2 **共享扫描**一次（采集所选类型的并集）→ Step 3 **一次裁剪**（适用全集）→ Step 4 **并行填充**多份。下文每步用「单类 / 批量」标注区分。

### Step 1　确定文档集合与边界（未指明则必须询问）

- 用户**明确点名一类**（如"生成用户手册"）→ 文档集合 = 该类，直接进入 Step 2（单类路径）。
- 用户**点名多类**（如"出用户手册和测试用例"）→ 文档集合 = 所点各类（批量路径）。
- 用户**未指明或含糊**（如"帮我生成项目文档""写个交付文档"）→ 用 `AskUserQuestion` **一次**问清，不要替用户决策：
  - **文档集合**（multiSelect）：`全部 4 类（交付套件，推荐）` / 需求规格说明书 / 系统设计文档 / 用户手册 / 测试用例文档 / 数据库表结构文档 / 自定义。交付 / 归档 / 验收场景默认推荐"全部 4 类"。**数据库表结构文档是技术参考类（非业务交付）**，需 PostgreSQL MCP（dbhub）已连接，详见 Step 3.7。
  - **覆盖范围**（整库 / 某个微服务 / 某些模块；若用户给了模块名则以之为准）
  - **目标读者**（开发 / 测试 / 业务方 / 终端用户——决定语言深浅，尤其用户手册 vs 设计文档差异巨大）
  - **是否需要 Word 输出**（默认只出 Markdown；要 Word 则在 Step 5 转换）

> 同时确认**项目名称**与**文档版本**（用于文件命名与封面）。这些信息贯穿后续所有步骤，问一次比反复打断高效。文档集合决定后续走单类还是批量路径。

### Step 2　扫描代码库（只读，派 Explore 子代理）

按文档集合读取 [references/doc-scan-guide](references/doc-scan-guide.md)，**通过 Task 工具派发 Explore 子代理**采集（避免在主上下文里逐文件读，缓解长文档生成的上下文压力）。子代理只读、不修改任何文件，产出一份**功能模块清单**（结构化摘要）：

| 文档类型       | 采集重点（详见 doc-scan-guide）                                                                   |
| -------------- | ------------------------------------------------------------------------------------------------- |
| 需求规格说明书 | 功能模块边界、主要功能与业务流程（业务事件级）、角色与功能可见性（读权限注解/指令归纳）、枚举字典                         |
| 系统设计文档   | 微服务拓扑、EF Core 实体与表结构、Controller /`I{Entity}Api` 接口清单、缓存、后台任务、依赖关系 |
| 用户手册       | Vue 页面与路由、按钮与操作入口、字段展示、枚举字典的中文标签                                      |
| 测试用例文档   | 功能点（来自页面 + 接口）、边界字段（必填 / 长度 / 枚举）、权限分支、接口入参出参、**各模块功能说明（用途/能力/规则）** |

- **单类路径**：派 1 个 Explore 子代理，按该类型的采集项扫描。
- **批量路径**（多类 / 全 4）：**只派 1 个 Explore 子代理**，prompt 指明扫描根目录 + **所选各类型采集项的并集**（直接合并 doc-scan-guide 对应小节；4 类同源、采集源高度重叠，见下文「各类型采集要点速查」矩阵），要求返回**一份**覆盖全部所选类型的结构化功能模块清单——不要为每类各扫一遍。

派发 prompt 必须自包含：指明扫描根目录、目标文档集合、要采集的代码位置清单（按 doc-scan-guide），并要求子代理**返回结构化清单**（模块名 / 实体 / 字段 / 接口 / 权限 / 字典），而非大段原文。

> **数据库表结构文档例外**：它的数据源是**实时 PostgreSQL（MCP）**，**不参与本步代码扫描**——其提取在 Step 3.7 单独进行。批量路径下，代码扫描只覆盖其它所选类型，数据库表结构文档的「表结构清单」由 Step 3.7 并行产出。

### Step 3　用户确认 / 裁剪范围（一次裁剪，适用集合内全部文档）

把扫描得到的**功能模块清单**呈现给用户，请其：

- **裁剪**：去掉本次文档不需要的模块（如内部运维模块不进用户手册）
- **补充**：指出扫描遗漏或尚未编码但需写入文档的功能（需求规格说明书尤其需要）
- **校对**：确认模块名称、归属服务的中文表述准确

> 这一步是质量阀门——避免把无关模块写进文档，也避免遗漏关键功能。用户确认后的清单才是后续填充的权威输入。**批量路径下，这份裁剪后的共享清单同时喂给所有文档**，是跨文档一致（模块清单 / 角色 / 实体对得上）的根本保障——不要每份文档各自再裁剪一遍。

### Step 3.5　启动 mock 前端并逐页截图（仅当 用户手册 ∈ 文档集合）

用户手册必须图文并茂，截图要反映系统真实界面与字段文案。**仅当文档集合中包含用户手册时执行本步**（单类用户手册、或批量路径含用户手册均执行）——不含用户手册则跳过。详细操作见 [references/user-manual-screenshot-guide](references/user-manual-screenshot-guide.md)，要点：

- **范围**：严格按 Step 3 用户**裁剪后**的模块清单截图，不截无关模块。
- **以 mock 模式启动前端**：确认 `VITE_MOCK_ENABLED=true`（字符串，非布尔；Admin 模板改 `.env` 后 `npm run dev`，默认端口 3009；非 Admin 改 `.env.development` 或用 `prototype` 模式）。mock 模式下前端用内置假数据完整运行全部模块、登录直接放行、无需后端——既保证截图真实，又零外部依赖与数据风险。
- **逐页截图**：用 **Playwright MCP**（`playwright@claude-plugins-official` 插件，会话内已启用，仓库无需任何 npm 依赖）的 `browser_navigate` / `browser_snapshot` / `browser_take_screenshot`（`fullPage: true`），从主界面点左侧菜单进入每个模块（贴近用户真实路径），列表页与新增/编辑弹窗分别截图，落盘到 `docs/images/user-manual/{模块key}-{视图}.png`。
- **同步记录功能流程**：截图过程中记录每个模块的入口路径、按钮文案、字段标签、操作顺序——这是 Step 4「操作步骤」「字段说明」文案的**权威来源**，手册文字必须与截图页面一致，杜绝臆造。
- **产出**：一份「截图清单」（模块 → 图片相对路径 → 关键操作/字段记录），供 Step 4 把模板中的截图占位符（`![...](images/...)`）替换为真实相对路径。

> **优雅降级**：仓库无前端代码、mock 数据缺失、dev server 启动超时/端口占用、或 Playwright MCP 不可用（备选 Playwright CLI 也无）时，**不阻断**手册生成——模板截图占位符原样保留，在文末「备注」列出「待补截图清单：模块 → 失败原因」，并提示用户环境就绪后可单独重跑本步补齐。降级判定依据来自 Step 2 扫描产出的「mock 截图可行性摘要」（见 doc-scan-guide 用户手册采集表）。

### Step 3.6　批量事实确认（仅批量路径）

多类 / 全 4 路径下，**不要让每个填充子代理各自打断用户**问业务事实。主上下文基于共享清单，对**跨文档共需、代码无法确定**的事实做**一次合并 `AskUserQuestion`**：

- 业务背景 / 项目背景（需求规格、系统设计、用户手册共用）
- 主要功能 / 用例的优先级 P0 / P1（需求规格为"主要功能"标注优先级，测试用例为"用例"标注优先级，共用同一套优先级口径）
- 验收标准（需求规格）
- 非功能性指标数值（需求规格、系统设计）

把这一轮的答案连同共享清单一起下发给各填充子代理。若某文档仍有**该文档独有**的未知项，子代理留 `[待用户确认：...]` 占位并在文末「备注」汇总，**绝不臆造**（沿用 Step 4 原则）。单类路径无需本步——直接在 Step 4 单次追问即可。

### Step 3.7　经 PostgreSQL MCP 提取表结构（仅当 数据库表结构文档 ∈ 文档集合）

数据库表结构文档的表 / 字段 / 类型 / 注释来自**实时 PostgreSQL**，不经代码扫描。**仅当文档集合中包含数据库表结构文档时执行本步**（单类、或批量路径含它均执行）——不含则跳过。详细操作见 [references/database-schema-extract-guide](references/database-schema-extract-guide.md)，要点：

- **前置硬依赖**：确认 dbhub MCP（服务名 `postgres`）已 `✔ Connected`（看会话内是否可用 `execute_sql` / `search_objects`，或 `/mcp`）。**未连接则中止**——引导用户先跑 `thirdnet-fullstack:thirdnet-mcp-setup` 挂 dbhub 并批准连接后重试，**不降级为代码扫描**。
- **选库与范围**：dbhub 已连到具体 DSN（`thirdnet-mcp-setup` 时定）；本步用 `AskUserQuestion` 让用户选要文档化的 schema / 表（默认全部用户表，排除系统 schema；`public` 框架表是否纳入由用户定）。
- **提取**：用 dbhub 两工具——`search_objects` 枚举 schema / 表 / 列 / 索引；`execute_sql` 跑 catalog SQL（指南内嵌即用片段）取**表用途（`obj_description`）+ 字段注释（`col_description`）+ 类型 + 可空 + 默认值 + 主键 / 唯一**，并发现字典表取枚举取值。
- **「备注」= 结构 + 语义标注**：结构元数据（主键 / 可空 / 默认 / 唯一）+ 语义（审计字段 `created_by/time` 等、枚举字典映射；推断项标「（推断）」）。`xmin` 乐观锁是系统列、不进字段表，文档说明里统一一句话带过。
- **产出**：一份「表结构清单」（schema 清单 + 每表的表名 / schema / 表用途 / 字段行：列名 / 类型 / 注释 / 备注 + 枚举字典），供 Step 4 填 `database-schema-template.md`。

> 全程只读，不执行任何 DML/DDL。表 / 列无 `COMMENT` 时填 `[未设置注释]`，可由命名推断并标「（推断）」，不臆造——所有推断项在文末「备注」汇总。

### Step 4　按模板填充

读取对应 `references/*-template.md`，**逐节**用 Step 2/3（批量含 Step 3.6）的内容替换占位符（`[项目名称]`、`[模块名]`、表格行等）。填充须遵循：

- **能从代码确定的**（字段名、接口路由、表结构、权限串、字典值）→ 直接填，保持与代码一致
- **代码无法确定的**（业务背景、优先级 P0/P1、验收标准、非功能性指标数值）→ 单类路径用 `AskUserQuestion` 集中追问；批量路径用 Step 3.6 已收集的答案。**绝不臆造**
- 模板中的「填写说明 / 提示」文字在最终文档中删除
- 同类重复结构（如多个模块的接口表）按模块复制填充，不要遗漏
- **用户手册特有**：「操作步骤」「字段说明」文案须与 Step 3.5 截图记录的实际按钮/字段一致；模板中的截图占位符（`![...](images/...)`）替换为 Step 3.5 产出的真实相对路径（如 `![用户列表](images/user-manual/user-list.png)`）。降级时占位符保留。
- **数据库表结构文档特有**：直接用 Step 3.7 的「表结构清单」逐表填 `database-schema-template.md` 的「表结构明细」（每表字段表 `列名 | 类型 | 注释 | 备注`）——表用途来自 `obj_description`、字段注释来自 `col_description`、备注按「结构 + 语义标注」拼装；推断项标「（推断）」并汇总到文末「备注」。

**单类路径**：在主上下文直接填充并 Write 单个文件。

**批量路径**（多类 / 全 4）：**在同一消息并发派 N 个 `general-purpose` 子代理**（每类一个，参考本插件 `backend-developer` / `frontend-developer` 的子代理派发模式）。每个子代理 prompt 自包含：

- 文档类型 + 其模板路径 `references/{type}-template.md`
- Step 3 裁剪后的**共享清单** + Step 3.6 的**事实答案**
- 写作原则（见上文「文档写作原则」：不堆砌代码细节、用业务语言、读者适配）
- 用户手册子代理另附 Step 3.5 的**截图记录与相对路径**
- 输出路径 `docs/{类型}-{YYYYMMDD}.md`，要求独立 `Write`

各子代理互不依赖、并发完成，主上下文等待全部返回。这样每份文档都在独立上下文里生成，规避长上下文后半段质量下滑，也最快。

> 填充时若发现代码与既有 `spec.md` / `plan.md`（backend/frontend workflow 产出的文档）冲突，以代码为准并在文末「备注」标注差异，提示用户核对。

### Step 5　输出（Markdown，可选 Word）

- **落点**：默认写入项目**根目录的 `docs/` 文件夹**下，命名规范 `docs/{文档类型}-{YYYYMMDD}.md`（如 `docs/系统设计文档-20260707.md`）。批量路径产出 N 个文件（每类一个）。若根 `docs/` 不存在则创建。用户另有指定路径时从其要求。用户手册的截图随 `docs/images/user-manual/` 一并产出（与 `.md` 同 `docs/` 根，相对路径 `images/user-manual/xxx.png`）。
- **Word 转换**（用户在 Step 1 要求时）：调用本插件内置的 `md-to-word` 技能（`skills/md-to-word/`，命名空间 `thirdnet-fullstack:md-to-word`），由其 `scripts/md_to_docx.py`（python-docx，无 pandoc 依赖）将 Markdown 转为同名 `.docx`。批量路径对产出的每个 `.md` 逐个转换。本技能与 md-to-word 同属一个插件，无需额外安装。转换前提示用户确认依赖（`pip install python-docx markdown Pillow`）。
- **完成后**：告知用户**全部产物路径**（批量时列清 N 份 `.md` 及对应 `.docx`），并提示「文档与代码同源，后续代码变更后可重新生成以保持同步」。

## 各类型采集要点速查

> 完整采集清单（按文档类型分别列出"读哪些代码、产出什么"）见 [references/doc-scan-guide](references/doc-scan-guide.md)。

| 维度                      | 需求规格    | 系统设计      | 用户手册      | 测试用例        |
| ------------------------- | ----------- | ------------- | ------------- | --------------- |
| 后端实体 / 表             | ◐ 数据需求 | ◉ 数据库设计 | –            | ◐ 边界字段     |
| Controller / 接口         | ◐ 接口需求 | ◉ 接口设计   | –            | ◉ 接口用例     |
| 前端`I{Entity}Api` 契约 | ◐ 接口需求 | ◉ 类型映射   | –            | ◐ 入参出参     |
| Vue 页面 / 路由           | ◐ 主要功能 | ◐ 模块划分   | ◉ 操作步骤   | ◉ 功能用例     |
| 权限（RBAC）              | ◉ 角色权限 | ◉ 安全设计   | ◐ 可见性说明 | ◐ 权限分支用例 |
| 枚举字典                  | ◐ 业务规则 | ◐ 字段含义   | ◉ 字段标签   | ◐ 枚举边界     |

（◉ = 主要来源；◐ = 辅助参考；– = 通常不涉及）

> 上表只覆盖 4 类**业务交付文档**的代码扫描来源。**数据库表结构文档**的数据源是**实时 PostgreSQL（MCP）**，不走代码扫描矩阵——其采集见 Step 3.7 / [database-schema-extract-guide](references/database-schema-extract-guide.md)。
