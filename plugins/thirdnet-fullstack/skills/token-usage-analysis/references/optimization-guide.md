# Token 节省优化建议知识库

按「正常性判定阈值 → 现象 → 典型原因 → 建议 → 预期节省」组织。诊断时只采用有报告数据支撑的条目，引用数据佐证；建议按预期节省幅度排序，给可执行操作步骤。

## 1. 正常性判定阈值表（体检基准，先判「是否正常」再诊断）

报告第一屏给总评结论，随后逐项判定。**ZCode 脚本路径由 `analyze_token_usage.py` 的 `THRESHOLDS` 常量自动判定；/context 粘贴、Claude transcript、手报数字等非脚本来源由代理按本表人工判定**——两处阈值必须保持同步，改动需一起改。

| 检查项 | ✅ 正常 | ⚠️ 偏高 | ❌ 异常（消耗过大） |
|--------|--------|---------|-------------------|
| System prompt 占窗口 | ≤10% | 10–20% | >20% |
| 内置工具定义占窗口 | 仅展示不判级（客户端注入基线，不可优化） | | |
| MCP tools 占窗口 | ≤10% | 10–20% | >20% |
| Messages 占窗口 | ≤50% | 50–70% | >70% |
| 剩余空间 Free space | ≥40% | 20–40% | <20%（接近 autocompact） |
| 缓存读 / 累计输入 | ≥80% | 60–80% | <60%（缓存频繁失效） |
| 子代理累计消耗 / 主会话累计输入 | ≤1× | 1–3× | >3× |
| 累计输入 / 窗口占用倍数 | 参考项不判级（见下方白名单） | | |

**总评规则**：任一 ❌ → 🔴 异常；无 ❌ 有 ⚠️ → 🟡 轻度偏离；全部 ✅ → 🟢 正常；无可判项 → ℹ️ 数据不足（缺窗口数据时提示 `--window N` 或 /context 补充）。异常项按 ❌ → ⚠️ 顺序点名，原因分析与优化建议优先针对它们。

**正常机制白名单**（看似异常、实为正常，不报警不下建议）：

- 累计输入为当前窗口占用的数十倍——每轮全量重发上下文所致，缓存读已大幅降费；真正要控的是轮次数与上下文体积；
- 缓存读数值巨大——是缓存命中，好事，不是浪费；
- 内置工具定义占比固定——客户端注入，用户不可控；
- 分析当前会话时统计脚本自身调用产生的新记录——属正常现象。

## 2. 分类占比诊断映射

### System prompt 偏大（> 10%）

| 典型原因 | 判断依据 | 建议 | 预期节省 |
|---------|---------|------|---------|
| 启用插件/技能过多（每个技能的 name+description 常驻） | 装有多个插件、大量技能 | 禁用低频插件/技能（ZCode：`~/.zcode/cli/config.json` 的 enabledPlugins；Claude Code：`/plugin` 管理） | 每禁用一个插件约省其全部技能元数据之和 |
| 钩子注入过长 | 使用带 prompt 注入的 hooks | 精简 hook 文案 | 视文案长度 |
| CLAUDE.md / AGENTS.md 过长（Memory files 大） | Memory files 占比高 | 精简至要点、长内容拆到按需加载的 references | Memory files 数值 × 80% 左右 |

### System tools 偏大

内置工具定义（Read/Edit/Bash/Agent 等）由客户端注入，**用户基本不可控**——如实说明即可，不要给无法执行的建议。

### MCP tools 偏大（> 10%）

| 典型原因 | 判断依据 | 建议 | 预期节省 |
|---------|---------|------|---------|
| 启用的 MCP 服务器过多 | 脚本按服务器分组，一眼定位最大者 | 禁用本次任务用不到的服务器（browser/playwright、documents/docx、pdf、spreadsheets、presentations 等文档类插件单家常占 1–4%） | 该服务器全部工具定义之和，每轮调用都省 |
| 单服务器工具数过多 | 如 playwright 25 个工具 ~6K tokens | 任务不需要浏览器自动化时整家禁用，而不是逐个工具关闭 | 同上 |

### Messages 偏大（> 50%）

| 典型原因 | 判断依据 | 建议 | 预期节省 |
|---------|---------|------|---------|
| 长对话自然累积 | 消息条数多、占比随时间增长 | `/compact` 压缩历史；或开新会话（携必要结论交接） | 压缩后 Messages 通常降至 10–25% |
| 大文件整读 | Top-N 中出现单条数 K 的工具结果（Read 全文） | Read 带 offset/limit 分段读；先 Grep 定位再读片段；超大文件交给子代理读、只回结论 | 该条目全额（后续每轮都省） |
| 命令输出冗长 | Top-N 中出现长 Bash 输出 | 命令后接 `head`/`tail`/`wc -l` 截断；构建类输出只要末尾结论 | 同上 |
| 助手推理（reasoning）块累积 | ZCode 脚本「消息：assistant / reasoning」占比高（常 20–35%） | 属客户端行为，间接缓解：减少反复试错轮次、一次给足约束；必要时 compact 一次性清掉历史推理块 | compact 后该分类清零 |
| 系统提醒（system 消息）多 | 「消息：system / text」占比高 | 减少触发大体积注入的操作（如频繁全量 todo、大 git status） | 视注入频率 |
| 图片/二进制入上下文 | Top-N 中 tool 结果含图片读取 | 避免不必要的整图读取；需要时降分辨率/裁剪 | 单图通常数 K tokens |

### Free space 偏低（< 40%；< 20% 需立即行动）

- 立即行动（< 20%，体检 ❌）：主动 `/compact`（保留任务要点）或开新会话交接，避免被动 autocompact 丢失关键上下文；
- 提前关注（20–40%，体检 ⚠️）：长任务把探索/读取类工作派发给子代理（独立上下文），主会话只留结论，延缓占用增长。

## 3. 累计消耗与子代理诊断（配额口径）

| 现象 | 典型原因 | 建议 |
|------|---------|------|
| 累计输入远大于窗口占用（如数十倍） | 轮次多、每轮全量重发上下文 | 属正常机制（缓存读已大幅降费）；真正要控的是**轮次数**与**上下文体积**——两者乘积即累计消耗 |
| 缓存读占比低（< 80%） | 频繁改动上下文头部（system 段）导致缓存失效 | 减少会话中途启用/禁用插件、修改配置等改变前缀的操作 |
| 子代理消耗高于主会话 | 任务书过宽、搜索范围过大、并行过多 | 收窄任务书（明确目录/关键词/期望产出）；要求「只回结论不回原文」；控制并行数（2–3 个以内）；探索类限定搜索广度 |
| 子代理输出大 | 让子代理回贴了大量文件内容 | 任务书显式要求汇总性结论 + 路径引用 |

## 4. 通用原则

1. **建议必须绑定数据**：每条建议引用报告中的具体分类/条目（如「playwright 25 个工具 ~6K，占 5.8%」）；
2. **按预期节省排序**：优先给占比大头且可立即执行的动作；
3. **区分一次性与持续性**：禁用 MCP 是每轮持续节省；compact 是一次性释放——两类都给时分开标注；
4. **不臆造**：来源数据没有的分类（如 /context 无 reasoning 细分）不下对应结论；
5. **给出操作步骤**：每条建议附具体命令或设置位置。
