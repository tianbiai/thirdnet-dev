# 阶段检查清单模板

> 何时读：进入对应阶段（冻结门 / 合并预检 / 对照验收）时。
> 权威源：《代码发布管理-原型驱动流程.md》§4 / §8。

## 冻结门清理清单（阶段 1 → 2，确认门 B）

> 为什么必须清理：阶段 2 采用**整体 `svn merge`**，原型分支上的所有代码（含被废弃的实验代码）都会进入主干。冻结前不清理，主干历史会被污染（源文档 §8.1）。

进入合并前，逐项确认原型分支已清理：

- [ ] 废弃的实验性页面（未被 spec 收录的 `views/` 页面）已删除
- [ ] 临时调试用的 Mock 数据（硬编码测试值、console 调试输出）已清除
- [ ] 注释掉的死代码块已删除
- [ ] 未接入路由 / 菜单的孤儿页面已处理（接入或删除）
- [ ] `IXxxApi` 契约已稳定，不再有「待定」字段
- [ ] 已与产品确认功能范围冻结，不再增删

用户确认以上清理完成后，方可触发确认门 B 进入合并。

## 合并预检清单（阶段 2，合并前）

源文档纪律：合并前两边工作副本都提交到最新。

- [ ] 原型分支 `Park-PT{r_base}` 工作副本 `svn status` 无输出（已全部提交）
- [ ] 主干 `Park` 工作副本 `svn status` 无输出（已全部提交）
- [ ] 已与前端协同确认工厂文件（`src/api/modules/{app|manager}/*.ts`）的合并风险
- [ ] 已确认无其他人在主干并行写同一模块的真实实现（时序纪律，源文档 §8.3）

预检通过后，触发确认门 C 执行 `svn merge`。

## 合并冲突处理清单（阶段 2，merge 后）

`svn merge` 后在主干工作副本执行 `svn status`，按此清单处理：

- [ ] 记录所有冲突标记 `C` 文件
- [ ] 重点检查工厂文件 `src/api/modules/{app|manager}/*.ts`（高发冲突点）
- [ ] 逐个冲突文件人工解决（本技能不自动改业务代码）
- [ ] 解决后 `svn status` 确认无残留 `C` 标记
- [ ] `svn commit -m "merge: 合并原型分支 Park-PT{r_base} 到主干"`

## 对照验收清单（阶段 4，测试用）

> 用途：测试人员以**原型服务器为功能验收基线**，在测试服务器对照验证真实实现是否与原型功能一致（源文档 §4.10）。

模板（按模块填写）：

```
【迭代N 对照验收】模块：{模块名}

| 功能点 | 原型服务器表现（Mock） | 测试服务器表现（真实） | 一致？ | 备注 |
|--------|----------------------|----------------------|--------|------|
| 列表查询 | {期望} | {实际} | ☐ 是 ☐ 否 | |
| 新建 | | | ☐ 是 ☐ 否 | |
| 编辑 | | | ☐ 是 ☐ 否 | |
| 删除 | | | ☐ 是 ☐ 否 | |
| {自定义功能} | | | ☐ 是 ☐ 否 | |

验收结论：☐ 通过  ☐ 有 bug（见 Bug 分流）
```

## Bug 分流判定清单（阶段 4）

测试发现 bug 后，按来源分流（源文档 §4.11）：

- [ ] **当前迭代的 bug** → 直接在主干 `Park` 修复。
- [ ] **已发布正式版的 bug** → 走 BF 子流程：
  - 确认该 bug 所在的正式版 revision `r_bf`
  - 建 `Park-BF{r_bf}` 分支修复
  - 测试发布清单（分支 `Park-BF{r_bf}`）
  - 通过后正式发布 + 合并回主干 + 删 BF 分支
  - 若涉及 DB schema 变更 → 提示联系运维还原测试库

## 删分支确认清单（阶段 5，确认门 D）

删除原型分支前确认：

- [ ] 该原型分支已合并回主干（mergeinfo 完整）
- [ ] 合并后的主干已通过测试服务器验证
- [ ] 分支内无尚未合并的孤立改动
- [ ] 已确认不再需要回溯该分支

确认后触发确认门 D 执行 `svn delete`。
